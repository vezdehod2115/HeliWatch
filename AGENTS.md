# AGENTS.md

Правила работы над HeliWatch (Android-приложение на Tauri v2) — для всех агентов и участников проекта.

## Обязательное правило

ПРАВИЛО GIT (коммит): В конце этапа выполняй git add . и git commit -m "..." двумя ОТДЕЛЬНЫМИ вызовами терминала (не используй &&, в Windows PowerShell это вызывает ошибку).

ПРАВИЛО GIT (пуш): После выполнения git commit всегда отправляй изменения на GitHub отдельной командой git push (не объединяя её через &&, в Windows PowerShell это вызывает ошибку). Работа не считается завершённой, пока изменения не отправлены на GitHub.

## Definition of Done этапа

Этап считается завершённым только после всех шагов ниже. Каждый шаг — отдельный вызов терминала; оператор `&&` в PowerShell не использовать.

1. **Сборка и проверки.** `pnpm build`, `cargo check`, тесты этапа и `pnpm android:doctor` проходят. Debug APK пересобран из текущего кода и лежит в `release/heliwatch-<версия>-debug.apk`.
2. **Документация и версия.** Статус этапа в `PLAN.md`, `README.md` и версия во всех файлах (`pnpm version:set X.Y.Z`) обновлены. После сборки `git status` не должен содержать незакоммиченных правок исходников.
3. **Коммит и пуш.** Тремя отдельными командами: `git add .`, затем `git commit -m "<краткое описание>"`, затем `git push`.
4. **Аннотированный тег.** `git tag -a v<версия> -m "HeliWatch v<версия> — <этап>"`, затем отдельной командой `git push origin v<версия>`. Тег всегда указывает на коммит этапа, который запушен в `origin`.
5. **GitHub Release.** Подготовь временный файл заметок вне репозитория с подробным ченджлогом изменений этапа и опубликуй релиз со свежим debug APK:

   ```powershell
   gh release create v<версия> "<ПУТЬ_К_APK>" --title "HeliWatch v<версия>" --notes-file "<ВРЕМЕННЫЙ_ФАЙЛ>"
   ```

   APK — актуальный debug-билд, заголовок — строго `HeliWatch v<версия>`.
6. **Уборка и запрет CHANGELOG.md.** После публикации удали временный файл заметок. Не коммить его и не добавлять `CHANGELOG.md` в репозиторий: подробный ченджлог этапа живёт в описании GitHub Release.
7. **Проверка релиза.** `gh release view v<версия>` показывает нужный тег, прикреплённый APK и заметки этапа. Только после этого этап сдан.

`gh` должен быть авторизован (`gh auth status`); если GitHub CLI не в `PATH`, используй полный путь к `gh`.

## Как это применяется

- Этап или задача считаются завершёнными только после коммита, пуша, тега и опубликованного GitHub Release: работа без релиза не сдаётся.
- Перед коммитом: сборка и проверки проходят, статусы в `PLAN.md` и `README.md` обновлены.
- Сообщение коммита — краткое и по сути изменений, например: `этап 1: каркас, два WebView, тач-роутинг, тема`.
- Порядок и формат вызовов: `git add .`, затем `git commit -m "..."`, затем `git push`, затем `git tag -a ...`, затем `git push origin v<версия>` — каждый отдельным вызовом терминала, без объединения через `&&`.
- Архитектура, протокол, версии и этапы — в [PLAN.md](PLAN.md); ченджлог этапа — в описании GitHub Release, а не отдельным файлом в репозитории.
